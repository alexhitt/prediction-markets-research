**Risks:**
- **EMOS cold start (30 days):** First 7-14 days use naive Gaussian from ensemble spread. Shadow trade accuracy will be lower initially. Mitigated: cold start plan has explicit phases.
- **Polymarket stops creating these markets:** Low probability (markets have been daily for 4+ days with $100K+ volume). If it happens, we detect it immediately (Gamma returns empty).
- **METAR station outage:** Occasional. Mitigated: skip city for that invocation, log the gap.
- **Rate limiting:** Not observed for Gamma or METAR at current rates. If hit, back off and reduce frequency.

No sensitive surfaces detected (no auth, no payments, no PII, no secrets).

## 6. Approach Options

### Approach A: Monolithic Script + EMOS Module (SURVIVOR)

**Core idea:** Single `run_asian_weather_shadow.py` (~500 lines) with all data fetching, shadow trade logic, bin death tracking, and metrics computation inline. Separate `src/calibration/emos.py` (~200 lines) for EMOS training and inference. Run via cron every 10 minutes.

**Why it works:** This is a validation tool, not production infrastructure. Speed to data collection matters more than architectural elegance. A single script is easiest to debug, deploy, and kill if the edge doesn't exist.

**Main tradeoff:** All logic in one file. If the script grows past validation into paper trading, it will need refactoring. Acceptable — we explicitly plan to refactor only if the edge validates.

**Fastest validation step:** Run the script once manually, verify data appears in JSONL files.

**Scrutiny:** Passes all 4 points (premise, scale, simpler-alt, infrastructure). This IS the simplest viable approach.

### Approach B: Extend Existing Validation Pipeline (KILLED)

Killed at scrutiny Point 3 (simpler alternative): retrofitting the US-only, Fahrenheit, 2°F-bin validation pipeline to handle Celsius 1°C bins is MORE work than building fresh. The existing `polymarket_weather_validation.py` has US-specific GMM params, station configs, and bucket math hardcoded throughout.

### Approach C: Modular Package (KILLED)

Killed at scrutiny Point 1 (scale): a proper Python package with fetchers/, models/, trackers/ submodules is over-engineered for a validation script that may be killed in 14 days.

## 7. Recommended Path

**Approach A: Monolithic Script + EMOS Module**

**Causal chain trace:**
1. `/plan` implements the script → ~500 lines Python + ~200 lines EMOS module
2. Script runs via cron every 10 min → fetches Gamma, METAR, ensemble data
3. Logs snapshots, shadow trades (YES + NO), bin deaths, Delta_T → JSONL files
4. After 7 days → enough data for initial Delta_T measurement and shadow accuracy
5. After 14 days → readiness gate evaluates kill/promote criteria
6. **End result:** Binary decision on whether the edge is real and exploitable

Chain holds at every step. The output (kill/promote decision with data) is directly actionable. No step requires infrastructure that doesn't exist.

**Deployment:** Option C (hybrid) — run on laptop during US daytime hours. Covers South Asian (08:30-10:30 UTC) and European (12:00-14:00 UTC) confirmation windows. Accept missing East Asian overnight data initially. Add `caffeinate` + launchd if overnight data proves critical after first few days.
